在理解网络协议/数据包之前，你需要有一定的基础知识。

必要的基础知识(一)

IP、端口、ASN

IP ：网络层数据包发送和接收的地址，用于唯一定位一台主机或路由器节点，包含 32 位的位的 IPv4（如 192.0.2.1）与 128 位的 IPv6（如 2001:db8::1）。内网地址和公网地址都拥有不同的 IP 段。

端口：传输层 (如 TCP/UDP) 的最终目的地，范围是 0-25565，端口用于区分同一主机上的不同应用进程 (常见端口有 TCP 22: SSH、UDP 53: DNS 、 TCP 80: HTTP、TCP 443: HTTPS、UDP 443: QUIC 等)。

ASN： Autonomous System Number，自治系统编号，全球互联网由成千上万个拥有统一路由管理策略的大型网络（如运营商中国电信/AT&T、大型云厂商 AWS/Cloudflare）拼接而成，每一个独立自治网络称为一个 AS（自治系统）。ASN 是分给它们的唯一编号，用路由协议 (BGP) 计算数据包如何跨网传输。

就像送快递，快递是数据包，收发地址到具体的楼就像是 IP，门牌号就是端口，物业就是 ASN一样。

IP 有一个非常重要的区别：内网地址和公网地址。 你在命令行输入ipconfig/ip addr 之后，电脑上显示的地址可能是 192.168.1.10 ( 192.168.0.0/16 ) ，常见内网 IPv4 地址段还有 172.16.0.0/12、10.0.0.0/8。

这是常见的内网地址。家里另一台电脑也可能使用同一网段的地址，它们通过路由器上网。 家用 IPv4 网络通常会使用 NAT，即网络地址转换。路由器把多台设备发出的连接，转换为使用公网地址的连接，并记录对应关系。

所以，网站看到的源 IP，通常是你家路由器或上游 NAT 设备使用的公网地址，而不是电脑上的 192.168.1.10。

DNS：域名如何变成连接地址

DNS（Domain Name System，域名系统） 是一套分布式查询系统，负责把域名解析成连接所需的信息，但它本身不负责建立网站连接。

最常见的地址记录是：

记录类型作用
A返回 IPv4 地址
AAAA返回 IPv6 地址
CNAME表示这个名字是另一个名字的别名

基础的 A、AAAA 记录只提供 IP 地址。端口通常来自 URL 和协议默认值，例如 HTTPS 默认使用 443。现代 DNS 的 HTTPS、SVCB 等记录还可以提供更多服务参数，包括协议提示和 ECH 配置等。

我们习惯记一个域名，而不是某个IP 地址。 例如：访问 www.example.com，给 DNS 服务器发查询请求，DNS 返回一个 IP 地址 203.0.113.80，浏览器拿到地址后，才会连接这个地址上的服务。

加密 DNS

传统 DNS 通常使用 UDP 53。查询内容一般没有加密，路径上能够观察这些数据包的设备，可能看到你查询的域名。

常见的加密 DNS 方式包括：

  • DoT：通过 TLS 传输 DNS。
  • DoH：通过 HTTPS 传输 DNS。
  • DoQ：通过 QUIC 传输 DNS。

加密以后，你与解析器之间的网络观察者通常不能直接读取查询内容，但递归解析器仍然知道你查询了什么。

此外，目标连接的 IP、连接时间和流量大小也不会因为 DNS 加密而自动隐藏。

DNS 污染

这就是让你在 DNS 服务器查域名的时候给你返回一个错误的 IP，导致无法与该网站建立连接。 比如访问 github.com，DNS 服务器 223.5.5.5：

本应该解析到 ASN 是 microsoft.com 的 IP，图中新疆地区明显拿到了错误的 IP ，也就是新疆对 Github 进行了 DNS 污染。

代理场景的 DNS 解析

有两种常见方式：

  • 本地解析：你的设备查域名 -> 得到 IP -> 把 IP 交给代理服务器建立连接；
  • 远端解析：你的设备把网站域名交给代理服务器 -> 代理服务器查询 DNS -> 代理服务器连接目标。

这会影响：

  • 哪一侧的 DNS 解析器知道目标域名；
  • 你的接入网络是否可能直接看到该 DNS 查询；
  • 最终获得哪个 CDN 地址；
  • 是否受到本地 DNS 返回结果的影响。

很多所谓的“DNS 泄漏”，就是用户希望目标域名通过代理查 DNS ，实际却在本地发出了 DNS 查询记录，可以在 browserleaks 查看你的 DNS 服务器以及有没有 DNS 泄露。

不过，代理服务器自身的地址可能仍需要先解析。代理地址的解析 (你的代理节点可能是一个域名) 和目标网站地址的解析，是两个需要分别考虑的问题。

TCP、UDP 与 QUIC

TCP：提供可靠、有序的字节流 UDP：提供数据报传输 QUIC：运行在 UDP 上，实现自己的连接、流、可靠性和安全机制

QUIC 很适合与 TCP 比较，但它在传输层是 QUIC 放在 UDP 里面。

TCP 像一条有编号、会重传的连续传送带

假设应用要发送 ABCDEFGHIJ ，网络中可能出现丢失、重复和乱序。TCP 使用序号、确认、重传等机制，在正常工作时把它整理成可靠、有序的字节流交给接收方。

例如：

1
2
3

先收到：ABC
又收到：GHIJ
中间缺：DEF

TCP 会处理缺失部分。在缺口补齐之前，后面的字节通常不能作为连续字节流继续交付给应用。

TCP 还会进行流量控制和拥塞控制：

  • 流量控制关注接收方是否处理得过来。
  • 拥塞控制关注网络是否已经承受过多流量。

有握手和重传就意味着 TCP 适合 Web 浏览、文件传输、API 等对可靠性要求极高的场景。

TCP 有三次握手建立连接，加 TLS 需累加握手耗时：

1
2
3

客户端 → SYN
服务器 → SYN + ACK
客户端 → ACK

可以粗略理解为双方确认通信状态、交换初始序号并建立连接状态。这个握手没有完成网站身份验证，也没有自动给数据加密。

另一个必须理解的特点是：TCP 不保留应用消息怎么分割。

发送方分两次发送：

1
2

第一次：HELLO
第二次：WORLD

接收方可能一次读到：

1

HELLOWORLD

也可能分几次读到：

1
2
3

HE
LLOWO
RLD

所以，使用 TCP 的应用协议需要自己定义消息边界，例如使用长度字段、分隔符或者固定格式。这也是理解代理协议数据包格式的基础：协议中为什么经常会出现 长度、类型 这些字段。

UDP 是一次次独立投递数据包

UDP 无需像 TCP 一样握手，优势就是极低开销与延迟 (0-RTT)，但是丢包不重传、无原生拥塞控制，需应用层自理。

UDP 本身不负责保证：

  • 数据一定到达；
  • 数据按顺序到达；
  • 丢失的数据自动重传；
  • 对方已经建立了类似 TCP 的连接状态。

例如：

1
2

发送：数据包 1、数据包 2、数据包 3
收到：数据包 3、数据包 1

UDP 不会自动替应用补上数据包 2，也不会替应用恢复顺序。

如果应用需要可靠性、拥塞控制或会话管理，就要在 UDP 之上设计相应机制 (例如 QUIC)。

UDP 适合某些实时场景 (如游戏、语音通话等)，是因为应用可以自己决定如何处理过期数据。例如语音中，一个很晚才补回来的片段，可能已经没有播放价值。

但 UDP 不 一定比 TCP 快。中国国内运营商就经常对 UDP 包进行 QoS 限速。实际表现取决于应用设计、网络条件、丢包情况及上层机制。

QUIC 在 UDP 之上更完整的传输机制

QUIC 不只是把 TCP 数据简单装进 UDP。它自己实现了连接管理、确认、丢失恢复、拥塞控制和多流传输，并结合 TLS 1.3 建立安全连接。

QUIC 的握手耗时缩短至 1-RTT 或 0-RTT（快速重连）。

QUIC 的优点是应用层单连接多流解耦 (比如同一条 QUIC 连接，有三个流，一个请求网页，一个请求图片，一个请求 JS)，彻底消除了传输层队头阻塞；支持基于 Connection ID 的无缝连接迁移（如 Wi-Fi 切蜂窝网络不中断）。

QUIC 一个流内的数据通常仍然需要按顺序交付。但流 A 的某段数据丢失时，流 B 已完整收到的数据，可以继续交付，这缓解了 TCP 单一有序字节流造成的跨流等待。

不过，多个 QUIC 流仍然共享网络路径、连接资源和拥塞控制；一个数据包也可能包含多个流的数据。因此，丢包依然可能影响多个请求，只是阻塞机制有所不同。

HTTP/1.1、HTTP/2 与 HTTP/3

HTTP 定义了浏览器与网站之间如何表达请求和响应。现在访问一个普通网页，大部分请求都是通过 HTTP 协议传输的。

版本常见传输方式主要组织方式
HTTP/1.1TCP；HTTPS 时再使用 TLS文本形式的请求行、头部等
HTTP/2通常为 TLS + TCP二进制帧、多个流、头部压缩
HTTP/3QUIC，底层是 UDP映射到 QUIC 流、头部压缩
HTTP/2 存在明文运行方式，但浏览器里的常见部署使用 TLS。HTTP/3 使用的 QUIC 则结合了 TLS 1.3 安全机制。

HTTP/1.1 纯文本协议

它长这样：

1
2
3

GET /article HTTP/1.1
Host: www.example.com
User-Agent: ExampleBrowser

GET 是 HTTP 规定的请求方法，RESTful API 还规定了 POST、PUT、DELETE等。 /article 是 HTTP 规定的请求路径，后面 HTTP/1.1 是协议版本。 下面的Host、User-Agent 是请求头，比如网站认证用的 Authorization: Bearer token 就是请求头里的一行。

它表示客户端希望获取 /article。

它的瓶颈应用层队头阻塞。在同一个 TCP 连接上，请求只能串行响应（必须等上一个请求完整返回，才能发送下一个响应），浏览器通常通过对同一域名并发建立 6 个 TCP 连接来缓解此问题。

HTTP/2 把一条连接分成多个逻辑流

HTTP/2 基于 TCP，引入二进制分帧层（Binary Framing），将数据切分成帧，实现单连接多路复用，多个请求和响应在同一条 TCP 连接中交错并发传输；配合 HPACK 头部压缩与服务端推送。

也就是不同请求的数据被组织成帧，帧中带有流编号。接收方据此把交错到达的数据分配回各个请求，这样就能在一条连接中并发处理多个请求。

它的瓶颈是 TCP 层队头阻塞。底层仍是单一 TCP 连接，网络一旦丢包，TCP 的滑动窗口会停滞等待重传，导致所有并发 Stream 全部受阻。

HTTP/3 抛弃 TCP，把 HTTP 放到 QUIC (UDP) 上，利用 QUIC 的多个流

HTTP/3 的不同请求通常使用不同 QUIC 流。某个流丢失数据时，其他流已收到的完整数据，可以继续交付。HTTP/3 继承了 HTTP/2 的多路复用与流抽象，但由于底层 QUIC 各 Stream 独立维护序列号，单一流丢包只会导致该流重传，其他流完全不受干扰，头部压缩升级为适配失序传输的 QPACK。

这里的改进可以概括为：

  • HTTP/1：单个 HTTP 流，浏览器建立多条 TCP 连接
  • HTTP/2：多个 HTTP 流，共用一条 TCP 有序字节流
  • HTTP/3：多个 HTTP 流，利用 QUIC 的多个流

HTTP/3 仍然可能因为共享拥塞控制、应用依赖或头部压缩状态等原因发生等待，并未彻底消除了所有阻塞。

协议封装、外层流量与内层流量

协议封装指的是应用层协议，比如 HTTP/1.1 就是把内容按照 HTTP 规定的格式塞进 TCP 除了头之类的正文里传输。

外层 TLS 在代理服务器结束。代理解开这一层后，可以读取代理协议中的目标地址、认证信息等内容。如果里面承载的是浏览器与网站之间的 HTTPS，代理继续看到的仍然是内层 TLS 数据。

同一次访问中可以同时存在： 设备 ↔ 代理：一层加密 浏览器 ↔ 网站：另一层加密

而底层 TCP 通常是两段： 设备 ↔ 代理：一条 TCP 连接 代理 ↔ 网站：另一条 TCP 连接

两段 TCP 连接，并不妨碍浏览器与网站通过转发的字节流完成一套内层 TLS 会话。

加密基础：AEAD、密钥交换与前向保密

AEAD 同时提供内容保密和完整性验证

AEAD 是现代对称加密的标准范式（如 AES-GCM、ChaCha20-Poly1305），不仅保证数据的机密性（加密不可读），还同时生成消息认证码（MAC）以保障完整性（防篡改）；此外，它允许将未加密的元数据（如网络报头）一同纳入防篡改校验计算。

假设原始内容是 转账金额：100 ，只考虑保密性，是希望旁观者无法读取这个金额。 完整性则要求：攻击者即使截获通信，也无法把它有效修改成 转账金额：900，防止让接收方把修改后的内容当成合法消息接受。

AEAD 可以粗略理解为：

2
3
4
5
6
7

密文和认证标签
    = AEAD 加密(
        密钥，
        nonce，
        明文，
        附加认证数据
      )

然后接收方使用对应密钥进行验证和解密。这里的 nonce 可以理解为本次加密使用的编号或一次性参数。它通常不需要保密，但必须满足具体算法的使用要求。

不过，AEAD 也有限制：

  • 它不会自动隐藏密文长度
  • 它不会自动隐藏通信双方 IP
  • 它不会自动解决所有重放问题(重复发包)
  • 它验证的是数据与密钥之间的关系，不能单独证明密钥持有者就是你想访问的网站

最后一点，需要身份验证来配合，下一章的 TLS 证书验证就是为了解决它。
