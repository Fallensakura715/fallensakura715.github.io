必要的基础知识(二)

TLS 的加密、握手、证书与身份验证

TLS 处于应用层（如 HTTP、SMTP、DNS）与传输层（TCP）之间，旨在为上层应用通信提供端到端的数据机密性（防窃听）、完整性校验（防篡改） 与身份验证（防冒充）。它是早已被废弃的 SSL 协议的现代官方继承者，也是 Web 浏览器中 HTTPS 安全连接的底层支撑。

当前互联网主要运行 TLS 1.2（RFC 5246）与 TLS 1.3（RFC 8446）。TLS 1.3 相比 1.2 移除了静态 RSA 密钥交换、CBC 分组模式及脆弱哈希算法，将完整握手时延从 2-RTT 缩减至 1-RTT。

下面以常见的 TLS 1.3、基于证书的完整握手为例。

TLS 1.3 之所以能做到 1-RTT，是采用了推测式密钥协商，客户端在发送 ClientHello 时就直接预测服务端支持的椭圆曲线 (X25519、X25519MLKEM768 等) 并生成公钥分片（Key Share），从而在 1 个往返内完成握手：

ClientHello：客户端提出协商条件

一个 TLSv1.3 的 ClientHello 包长这样：

  • legacy_version：固定填 0x0303（即 TLS 1.2）。TLS 1.3 为了通过某些老旧防火墙/中间件，将实际版本协商移入扩展字段中。
  • random：32 字节密码学安全伪随机数。包含客户端时间戳或随机熵，用于抵御重放攻击，并在防降级机制中充当校验标记。
  • legacy_session_id：在 TLS 1.3 中已弃用，但在向后兼容模式（Middlebox Compatibility Mode）下可填充伪随机字节，避免中间设备断开连接。
  • cipher_suites：支持的 AEAD 加密套件列表。TLS 1.3 只保留了 5 种，最常见的是：
    • TLS_AES_128_GCM_SHA256 (0x1301)
    • TLS_AES_256_GCM_SHA384 (0x1302)
    • TLS_CHACHA20_POLY1305_SHA256 (0x1303)

关键 Extensions（扩展字段）：

  • supported_versions：强制字段。必须显式声明包含 0x0304（TLS 1.3），服务端根据此字段决定采用 1.3 还是 1.2。
  • server_name（SNI）：明文告知目标服务器的主机名（如 api.example.com），解决单 IP 多虚拟主机托管不同证书的路由问题。

    为什么需要 SNI？ 假设一台服务器或 CDN 节点同时承载 a.example.com 和 b.example.com，两者解析到同一个 IP。客户端刚建立 TCP 连接并进行 TLS 握手时，还未发送任何 HTTP 请求（Host 头还在后面），但服务器此时就必须决定拿出哪张证书来响应握手。SNI 就在这个阶段告诉服务器：我希望访问 a.example.com。 隐私隐患：在未启用 ECH 时，ClientHello 中的 SNI 是完全明文的，链路上的任何中间设备都能直接看到你正在访问哪个域名。

  • supported_groups：客户端支持的椭圆曲线列表，如 x25519 (0x001d)、secp256r1 (0x0017)。
  • key_share：客户端为上述曲线中优先级最高的曲线生成的临时公钥。例如选定 X25519 时附带 32 字节的公钥分片。
  • signature_algorithms：客户端信任的数字签名算法列表，如 ecdsa_secp256r1_sha256、rsa_pss_rsae_sha256，给服务端后续签发 CertificateVerify 时选择。

由于整个ClientHello是明文传输的，客户端提供的这些字段形成的特征就是 TLS 指纹，后续详细讲到。

ServerHello：服务端确认协商参数

  • legacy_version：同样回写 0x0303。
  • random：服务端的 32 字节随机数。
    • 防降级机制：若服务端支持 1.3 但降级与客户端协商 1.2，其 random 尾部 8 字节会被强制设置为特定魔数 444F574E47524401（“DOWNGRD\x01”）；客户端收到后若发现降级异常会立即终止连接。
  • cipher_suite：选定的单一加密套件（如 TLS_AES_128_GCM_SHA256）。
  • extensions -> key_share：服务端对应曲线生成的临时公钥分片。
    • 注：若服务端不支持客户端在 key_share 中提供的曲线，会回送 HelloRetryRequest（HRR），要求客户端更换曲线重新发送 ClientHello，握手自动退化为 2-RTT。

EncryptedExtensions：加密扩展参数

从这个字段开始，传输内容全部由协商出的临时密钥加密。它包含了原属于 ServerHello 但不影响密钥派生的扩展参数，例如 ALPN（协商应用层协议：h3、h2、http/1.1 等）。

Certificate：服务端的身份凭证

包含一个完整的 X.509 证书列表（证书链），按顺序存放：服务器叶子证书 -> 中间 CA 证书 -> （根 CA 证书，通常省略由客户端本地提供）。

CertificateVerify：服务端向客户端证明自己真正拥有该证书对应的私钥

证书原本就是公开的，任何中间人都可以把正牌网站的证书保存下来转发给你。因此服务端必须证明自己手里真正握有该叶子证书对应的私钥：

  • 服务端签名：服务端计算从 ClientHello 开始到目前为止所有已收发握手报文的 Hash，拼接上固定上下文前缀后，使用叶子证书对应的私钥生成数字签名。
  • 客户端验签：客户端提取叶子证书里的公钥，结合本地计算出的相同握手报文哈希，对签名执行数学验证。验签通过，即证明正在通信的服务端确实拥有该证书私钥，且此前所有握手报文未被篡改。

证书验证是抵御中间人攻击（MITM）的核心环节。

证书链与 X.509 验证流程

客户端收到服务器证书后，按如下流水线严格校验：

  1. 域名匹配：
    • 提取访问 URL 中的域名，与叶子证书中的 SAN 扩展做字符串/通配符匹配（优先使用 SAN，忽略旧的 Common Name）。不匹配则触发 SSL_ERROR_BAD_CERT_DOMAIN。
  2. 有效期校验：
    • 以本地受信任时间戳为基准，必须满足：$\text{Not Before} \le \text{Current Time} \le \text{Not After}$。
  3. 信任锚点寻址与证书链构建：
    • 根据叶子证书的 Issuer 查找握手报文中附带的中间证书。
    • 再由中间证书查找其父级，直至在操作系统或浏览器的本地根证书信任库中找到自签名的根证书（Root CA）。若链条断裂或找不到受信任的根，直接报“不可信的签发机构”。
  4. 密码学签名校验：
    • 对证书链中每一级证书 $N$（从叶子到根）： $$\text{Hash} = \text{SHA256}(tbsCertificate_N)$$ $$\text{Verified} = \text{VerifySignature}(\text{PublicKey}_{N+1}, \text{Hash}, \text{SignatureValue}_N)$$
    • 用父证书的公钥解密并核验子证书的签名。
  5. 约束与权限校验：
    • 检查中间证书的 Basic Constraints 是否标记了 CA:TRUE（防止有人拿普通域名叶子证书去给别人签发假证书）。
    • 检查路径长度限制（pathlen）：若 pathlen=0，该中间 CA 绝不能签发下一级中间 CA。
    • 检查 Key Usage 是否允许签证书（keyCertSign）。
  6. 吊销状态检查
    • CRL（证书吊销列表）：下载 CA 定期发布的已作废证书序列号黑名单（延时高、体积大，已逐步淘汰）。
    • OCSP（在线证书状态协议）：向 CA 的 OCSP 响应服务器发送请求查询序列号状态（有延迟且暴露用户访问隐私）。
    • OCSP Stapling（装订）：服务端定期向 CA 请求带签名的 OCSP 响应，在 TLS 握手的 Certificate 阶段直接附带给客户端，由客户端离线校验 CA 签名，兼顾安全与性能。

在 TLS 1.3 中，Certificates 是加密的，直接用 抓包看不到明文；而在 TLS 1.2 中，证书是明文传输的，我们可以直接通过抓包看到完整的证书链结构。

针对 TLS 的 MITM (中间人攻击)

中间人攻击（Man-in-the-Middle Attack，简称 MITM）是指攻击者悄悄介入通信双方之间，拦截、监听、甚至篡改双方交互的数据，而通信双方却误以为正在与对方直接通信。

伪造/注入根证书可以直接 MITM 解密你的流量。

  • 攻击原理：抓包工具（如 Charles、Fiddler、Burp Suite）和企业上网行为审计（DLP/GFW）的工作本质就是“授权的 MITM”。
  • 操作手法：
    1. 攻击者动态生成一张颁发给 example.com 的证书，但签名者是攻击者自建的 CA（或伪造的根证书）。
    2. 如果受害者机器已被植入恶意根证书（例如通过恶意软件、公司 IT 统一推送策略或诱导用户手动安装），系统信任库（Trust Store）就会判定该伪造证书合法，TLS 握手顺利完成。
    3. 攻击者即可实时解密双向通信载荷。

证书绑定 (Pin 证书)

在移动 App、金融客户端内，硬编码预置目标服务器公钥的 Hash（Pin）。即使系统底层被安装了恶意根证书，只要 App 发现远程服务器的公钥与本地 Pin 不符，就直接断开连接。这也是为什么 iOS 安装 mitm 证书后，许多大厂 App 依然抓不到包/不能 mitm（直接断网报错）的原因。

Finished：握手状态的完整性自检

基于整个握手过程所有报文的 Hash，通过 HKDF 派生出的 finished_key 计算出 HMAC 校验码。双方各自生成并互相校验 Finished，确保没有任何中间人篡改过握手报文的任意一比特（防降级、防篡改）。
